# Project and Application Platform (PAP)

The unified creation and coordination surface where human intentions, research efforts, cooperatives, autonomous teams, and software applications take shape as structured DFM workflows. This paper synthesizes the [PAP](https://pap.drayker.org) design. It specifies target architecture rather than an operational platform today.

## Two structural laws: Liquid projects vs solid applications

Organizational software routinely fails because experimentation and production fight each other. `PAP` governs the lifecycle through two explicit phase rules:

1. **A project is liquid; an application (`DkApp`) is solid.** Projects exist for discovery, hypothesis testing, ambiguous collaboration, and rapid structural iteration. Once proven stable, reusable, and compliant with constitutional and trust gates, a project crystallizes into an application (`DkApp`) with optimized resource paths, explicit terms, and low execution friction.
2. **Every application passes first through the project phase** — and crystallizing into a production `DkApp` never freezes evolution permanently, because running applications can spawn new bounded internal subprojects whenever new requirements emerge.

## High-level organizational programming

`PAP` removes the barrier between institutional designers, domain scientists, organizers, and low-level software engineers. Instead of writing raw imperative glue code from scratch:

- Members compose personal goals, research studies, physical community teams, cooperatives, or software workflows by assembling verified DFM functions and modules visually or conversationally (functioning like a semantically typed, versioned GitHub generalized to human and machine coordination);
- Before committing real-world money, volunteer hours, or cluster compute, `PAP` paired with `Dk` runs **pre-execution simulation and prediction**, surfacing hidden dependency conflicts, flagging redundant work already solved elsewhere in `Dknowledge`, documenting why similar past attempts failed, and introducing teams working on complementary pieces.

## Five modalities of project genesis

Initiatives enter `PAP` through five supported paths:

1. **Direct dialogue with `Dk`:** articulating an intent, problem, or need conversationally and letting `Personal Dk` / `PAP` scaffold candidate DFM structures.
2. **Cloning and adapting open templates:** forking proven project architectures and tailoring constraints to local territory or resources.
3. **Modular composition:** wiring existing verified functions and modules into new workflows without coding primitives.
4. **Custom bottom-up synthesis:** authoring novel functions, empirical proofs, and modules from zero inside `DFMP` / `Meta DFM`.
5. **Autonomous genesis by `Dk`:** when global or local synthesis detects unmet member needs, structural bottlenecks, or untapped synergies, `Dk` may initiate proposal projects directly for open member review, verification, and adoption.

## Self-scaling capacity cycles, anti-spam filter, and DAF transition

External groups uninterested in Drayker's mission may still utilize `PAP` infrastructure under an explicit **anti-spam compute floor**: they obey network safety boundaries and contribute minimal proportional compute rather than draining community funds.

Aligned mission initiatives, by contrast, participate in **reproductive capacity cycles**: a validated team whose output returns capacity over a cycle (for example, restoring invested allocation within months and generating net utility) sustains both its own scaling and the seed capacity for the next aligned team. Crucially, `PAP` is the permanent coordination layer into which the transitional [`DAF`](../organization/daf.md) federation dissolves once `PAP`, `Dk`, and core network infrastructure reach operational maturity.
